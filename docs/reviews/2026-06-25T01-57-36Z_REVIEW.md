v1 ([`2026-06-24T22-38-29Z_REVIEW.md`](./2026-06-24T22-38-29Z_REVIEW.md)) whose §1

## BUGS (fabricated / inaccurate identifiers in the blueprint — rejected)

Verified against `canton-stablecoin` / spine / evidence repos (2026-06-24):

- **`VaultState` / `VaultConfig` as keyed contract templates** — do **not** exist
  as contracts. `VaultState` appears only in a test/model file
  (`canton-stablecoin/stablecoin-test/daml/Stablecoin/Test/VaultModel.daml`). The
  real surface is config (`VaultParams`) + state (`Vault`), separate contracts by
  ContractId.
- **`(operator, vaultId)` contract key + `fetchByKey`** — there are **no contract
  keys anywhere** in `canton-stablecoin` (or the spine). Daml-LF 2.1 is keyless.
- **`UpdateSharePrice`** — no such choice. The real oracle choice is
  `PriceOracle_UpdatePrice`.
- **ERC-4626 share-accounting / "vault shares" / share-exchange-rate** — not in
  the code; the real model is a **CDP** (collateral + debt). (Documented as an
  *external* reference pattern in `canton-stablecoin/RESEARCH.md`, attributed to a
  separate `ted-gc/canton-vault` repo — not this workspace's implementation.)
- **`TransferInstructionV2` / `AmuletAllocationV2`** — fabricated. Only
  `AllocationV2`, `AllocationRequestV2`, `HoldingV2` exist, and only as upstream
  `Splice.Api.Token.*` imports in `canton-token-template` tests.
- **`ComplianceRegistry` / `BlacklistValidator` / `ClaimsValidator`** — fabricated.
  The decided D1 model is the node-applied `D1ComplianceHook` data record, already
  correct in §3.

Confirmed-correct (kept): `Vault`, `VaultFactory` (`VaultFactory_OpenVault`),
`Vault_{DepositCollateral,WithdrawCollateral,MintStablecoin,BurnStablecoin,Liquidate,Close}`,
`VaultParams` (`minCollateralRatio`, `liquidationRatio`, `liquidationBonus`,
`stabilityFeeRate`), `PriceOracle` + `PriceOracle_UpdatePrice`, `BurnerCapability`
(template, no choices), `D1ComplianceHook` / `D2SeizureHook` (data records),
`KycClaim.subjectParty` / `TrustedIssuerRegistry` (canton-specs identity-hook),
the `zk-credential-gateway` primitives.

## ANTI-PATTERNS (in the blueprint — rejected)

- **Scope contradiction presented as a recommendation.** The blueprint frames the
  ERC-4626 share-vault as *the* lending architecture; `M3_LENDING_SCOPE.md` §B
  locks "contract-per-vault, NOT ERC-4626 share-accounting". The grant's ERC-4626
  mention is OZ's **cross-ecosystem experience**, not a commitment to a
  share-accounting vault on Canton. Adopting it would break the scope lock.
- **External-citation essay.** OCC IL 1170/1172/1174, FDICIA §36, SOX/ICFR, SOC 1
  Type 2, Chainlink Proof-of-Reserve, `ted-gc/canton-vault`, QuillAudits,
  PixelPlex, etc. — non-workspace, non-spec; barred by house conventions.
- **Oracle over-claim.** "the oracle's cryptographic signature is verified directly
  within the Daml transaction" via Chainlink — the real `PriceOracle` is an
  admin-signatory contract (Daml authorization *is* the signature); a Chainlink/PoR
  feed is a `[FUTURE]` external integration, not present. Not adopted.

## IMPROVEMENTS (integrated into `02-lending.md`)

1. **§1 (Contract-per-Vault vs. Share-Accounting) — defensive hardening.** Names
   the ERC-4626 share-vault as a deliberate departure from OZ's own ERC-4626
   lineage, and explicitly states the design is **keyless**: no
   `(operator, vaultId)`-keyed `VaultState`/`VaultConfig` + `fetchByKey`, no
   `UpdateSharePrice`; config (`VaultParams`) and state (`Vault`) are separate
   contracts by ContractId. Pre-empts exactly the blueprint's proposal.
2. **§3 (SCU Extension Story) — `[UPSTREAM]` retroactive-interface-instance note.**
   New interfaces are added by new templates/choices, not by retroactively
   re-instancing the deployed `Vault`; Daml 3.x removed retroactive interface
   instances. (Same reinforcement added to the DEX report for suite consistency.)
